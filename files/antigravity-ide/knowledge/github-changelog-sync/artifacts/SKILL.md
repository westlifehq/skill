# GitHub Changelog Sync Skill

此技能用于在代码同步到 GitHub（如 push、合并到 main、提交版本、发版）之前，自动扫描、检测、更新或创建仓库的 Changelog，确保所有变更都有持续、统一、可追溯的版本记录。

## 触发时机

当用户提及以下意图时，必须激活并执行此技能：
- “同步到 GitHub” / "Sync to GitHub" / "Push to repo"
- “推到仓库” / “提交代码” / “Git push”
- “更新 changelog” / “更新变更日志”
- “把这次改动记录下来” / “记录本次修改”
- “发版前补一下变更说明” / “更新 release notes”

---

## 核心工作流

AI 必须严格按照以下三步执行，严禁跳过任何步骤。

### 第一步：全仓扫描与识别（禁止默认新建）

1. **遍历文件系统**：优先使用 `list_dir` 或 `grep_search` 等工具，在整个仓库中搜索以下候选 changelog 语义文件（区分大小写）：
   - `CHANGELOG.md`
   - `Changelog.md`
   - `changelog.md`
   - `HISTORY.md`
   - `RELEASE_NOTES.md`
   - `release-notes.md`
   - `docs/CHANGELOG.md`
   - `docs/changelog.md`
2. **分析引用关系**：检查 `README.md`、`docs/` 目录或发布说明文档，查看是否有引用其他路径下的变更记录文件（例如 `docs/updates.md` 等）。
3. **主 Changelog 判定**：
   - 如果未找到任何候选文件，进入 **第三步（新建机制）**。
   - 如果只找到一个候选文件，该文件即为**主 Changelog**。
   - 如果找到多个候选文件，必须读取它们的内容 and 最后修改时间，判断哪个才是仓库“当前实际在用”的主 changelog（通常是记录最全、更新最频繁、或者在 README 中被链接的那个），并将该文件定为**主 Changelog**，其余文件不予操作，防止重复新建第二份变更日志。

### 第二步：读取与更新（增量修改）

1. **读取现有内容**：在写入前，必须使用 `view_file` **完整读取**主 Changelog 的现有内容，明确其现有的版本号格式、排版风格和记录习惯。
2. **禁止覆盖旧记录**：更新操作必须是**增量追加**，绝对不能清除、覆盖或精简已有的历史记录。
3. **倒序结构**：新版的变更日志必须采用“最新内容在最前面”的倒序结构，插入到文件头部或首个版本记录之前。
4. **生成详细变更**：收集本次修改的代码 diff 或文件状态，记录以下要素：
   - **变更时间点**：精确到天的日期（例如 `2026-05-22`）。
   - **版本号**：如果项目已有特定的版本号风格（如 `v1.2.3` 或 `1.0.0`），须沿用并递增；若无，可采用日期版本（如 `YYYY.MM.DD`）或咨询用户。
   - **提交/分支信息**：当前的分支名称或 commit hash（如果可获取）。
   - **修改的文件范围**：列出受影响的主要文件及目录。
   - **主要新增内容**：具体描述新增加的特性，禁止宽泛描述。
   - **主要修复内容**：具体描述修复的缺陷，禁止使用“修复了一些 Bug”等模糊字眼。
   - **行为变化 / 兼容性影响**：列出配置、API 或运行行为的破坏性变更或重要调整。
   - **风险与注意事项**：提醒用户同步后可能需要注意的运行风险。
5. **README 同步**：检查 `README.md` 中是否存在版本号标识、更新说明入口或 release notes 链接。如有，应同步将版本号和链接更新，但切勿引入与本次版本无关的改动。

### 第三步：新建机制

仅当第一步确认**整个仓库没有类似 changelog 的文件**时，才允许在仓库根目录下新建 `CHANGELOG.md`。
- 新建的文件必须采用清晰的 Markdown 格式，符合上述第二步的所有“详细变更记录要素”与“倒序结构”规范。

## 变更记录模板

更新或新建的主 Changelog 块应采用以下格式风格（可根据仓库既有风格自适应调整）：

```markdown
## [版本号] - YYYY-MM-DD

### 📝 变更概述
- **分支/提交**: `main` / `feat/changelog-sync` (Commit: `a1c2e3f`)
- **受影响范围**: `lib/`, `package.json`, `github-changelog-sync/`

### 🚀 新增功能
- 新增 `github-changelog-sync` 技能，支持在代码推送到远程仓库前自动同步 changelog。
- 引入自动化扫描逻辑，能够自适应识别包括 `CHANGELOG.md`、`HISTORY.md` 在内的 8 种以上变更日志语义文件。

### 🐛 缺陷修复
- 修复了在检测到多个 changelog 文件时重复创建新文件的错误，现在会智能合并到主 changelog。

### ⚠️ 破坏性变更与兼容性影响
- 无。

### 💡 风险与说明
- 写入前会执行本地读取以防覆盖。请在推送前进行人工确认。
```

## 示例与反模式

### 正确示例

1. **用户输入**：“准备把代码推到仓库，顺便帮我更新下变更记录。”
2. **AI 动作**：
   - 运行扫描，发现 `docs/changelog.md` 存在，且 `README.md` 中链接了它。
   - 读取 `docs/changelog.md` 的内容，发现当前版本为 `v1.1.0`。
   - 生成 `v1.1.1` 的详细变更日志，将修改过的 `server.js` 和 `package.json` 变动写入 `docs/changelog.md` 的最上方。
   - 更新 `README.md` 中的版本号为 `v1.1.1`。
   - 完成任务并提示用户已更新 `docs/changelog.md`。

### 反模式

*❌ 默认新建*
- 扫描都未进行，直接在根目录新建 `CHANGELOG.md`，导致仓库中同时存在 `Changelog.md` 和 `CHANGELOG.md` 两个文件。

*❌ 模糊描述*
- 在变更日志中写道：“更新了代码，修复了一些问题。”（不符合可审计、可追溯要求）

*❌ 历史覆盖*
- 写入新变更时，不小心把文件中旧版本的历史记录全部删除，只剩下了本次的记录。
